**How to read the evidence.** Each finding says how it is known:

- **Verified**: I ran it (a test, a script, a build, a browser run) and saw the result.
- **Code-read**: I read the code and the behaviour follows from it; I did not run it.
- **Reasoned**: it follows from how the platform or the design works; not run, and could be wrong.
- **Not measured**: a cost or size that nobody has measured on a real device or library.

Numbers marked "synthetic" come from `fake-indexeddb` under Node, which is slower than a browser's IndexedDB. They show a trend (linear, or not), not what a user would see.

**Priority.** _Now_: small, clear, do soon. _Next_: worth doing before more features. _Later_: real but not urgent. _Owner_: needs a decision or a device only the owner has. Effort: S (hours), M (a day or two), L (several days).

## 3. Data and integrity

### 3.1 Orphan index records after a delete during indexing (verified)

**Found.** `deleteBook` clears the index and status records of a book, but the index build writes a record after every batch (`ensureIndexNow`, `writeIndex`). If the book is deleted between two batches, the next batch writes the record again. Reproduced with `fake-indexeddb`: a six-page build, a delete after 40 ms, and afterwards both `searchIndex` and `searchMeta` held a record for the deleted id. The shelf search ignores such records (it filters by books on the shelf), so nothing shows, but they stay forever, are read by every query (`readAllIndexes` loads them all), and take storage. The shelf indexer makes this likelier than before, because it builds in the background while the person can delete.

**Fix.**

1. In `src/lib/search-index.ts`, make `writeIndex` write inside one transaction on `["books", "searchIndex", "searchMeta"]` and skip the write when `books` has no record for the id. The reader's index always has a book record, so nothing legitimate is lost.
2. In `indexShelfHeadless` (`src/lib/headless-index.ts`), after `ensureIndex` returns, do not count a book that is no longer on the shelf.
3. Repair what already exists: on the shelf's first load, delete every `searchIndex` and `searchMeta` record whose id is not in `books` (one cursor pass; cheap).

**Test.** Turn the reproduction into `tests/unit/search-index-orphan.test.ts`: build, delete mid-build, expect no record in either store. Mutation: remove the existence check and see it fail. Add a second test for the sweep (seed an orphan, run the sweep, expect it gone, expect a real book's record untouched).

### 3.2 Pages without text count as indexed (code-read)

**Found.** `ensureIndexNow` wraps each page's `extract(page)` in `try { … } catch { entries.push({ page, text: "" }) }`, so a page that throws is stored as empty and the book still ends `ready`. A scanned PDF page has no text layer and also yields `""`. The shelf line then says "7 of 7 indexed" for a library in which some books cannot be searched at all. Strategy item "unsearchable scans" (library health) needs exactly this number.

**Fix.**

1. Count empties while building: in `ensureIndexNow`, keep `emptyPages: number[]` on `SearchIndexRecord` (optional field, so old records stay valid) and fill it when `text.trim()` is empty, distinguishing "threw" from "empty" (`failedPages`).
2. Surface it: `ShelfIndexStatus` gains `textless` (books where more than, say, half the pages are empty). The shelf line becomes "… 7 of 7 indexed, 2 have little or no text" and the second clause links to a filtered view.
3. Use it: on a book card or in the reader's search tab, offer the existing OCR (`ocrEnabled`) for those books; when OCR text arrives it goes through the same index path.

**Test.** Unit: an `extract` that throws on page 2 and returns `""` on page 3 gives `failedPages = [2]`, `emptyPages = [3]`. E2E: import the sample PDF built with `makeSamplePdf` with one blank page and check the line.

### 3.3 Failed books are retried on every visit (code-read)

**Found.** `indexShelfHeadless` runs whenever `booksKey` changes, which includes every import and delete, and it re-attempts every book that is not `ready`. A book whose file cannot be opened (`openUnits` throws, or has zero units) is only counted in memory as failed; nothing is stored, so a corrupt EPUB is parsed again after every import. With several such books this is repeated CPU for nothing.

**Fix.** Persist the decision. In `searchMeta` (the cheap status record), store `{ status: "failed", reason, size, indexVersion }` when `openUnits` fails. Skip a failed book while its stored `size` and `indexVersion` are unchanged. Give Settings a list of "books that could not be indexed" with a Retry button that clears the record. The skip rule is the part to test: a failed book is not opened again on the next pass; after Retry, or after the file is replaced, it is.

### 3.4 Backup and restore scale with the whole library in memory (code-read)

**Found.** `exportBackup` puts every book's bytes in one object (`files["blobs/<id>"] = new Uint8Array(await blob.arrayBuffer())`), then `zipAsync` compresses them (at the default level, on EPUB, CBZ and PDF files that are already compressed, which gains almost nothing and costs time) and builds one `Blob`. `restoreBackup` reads the whole archive with `file.arrayBuffer()` and `unzip`s it into memory. A library of a few gigabytes of comics cannot be backed up or restored on a phone, and probably not on a desktop tab. There is also no limit on the declared sizes inside an archive, so a crafted `.nawiri.zip` can exhaust memory (a self-inflicted crash, not a data leak).

**Fix.** Keep the file format (so old backups still restore and `backup-legacy.test.ts` keeps passing) and change how it is written and read.

1. Write: use fflate's streaming `Zip` with `ZipPassThrough` for book files (no recompression), feed each entry from `blob.stream()` in chunks, and collect the output chunks into a `Blob` made of the chunk list (the browser can keep that on disk). Where `showSaveFilePicker` exists, write straight to the chosen file instead. Write `manifest.json` first so a restore can read it early.
2. Read: use fflate's streaming `Unzip` with `UnzipInflate` and `UnzipPassThrough`, reading `file.stream()`; assemble one book at a time into a `Blob` and store it before the next. Read `originalSize` from each entry header and refuse an entry or a total above a budget (for example, the file's own size times a ratio, and an absolute cap the owner can raise).
3. Cheap first step, before the streaming rewrite: store book files at level 0 (`[bytes, { level: 0 }]`) in `exportBackup`.

**Test.** Unit with `fake-indexeddb`: a 200 MB synthetic library, with `process.memoryUsage().heapUsed` and `arrayBuffers` sampled during export and restore (the streaming version must stay well under the library size); a restore of an archive that declares a huge `originalSize` is refused with a message. The existing `backup.spec.ts` specs stay as they are and must keep passing; they are the proof that the format did not change.

### 3.5 `listBooks()` reads every cover (code-read)

**Found.** Cover images are stored in the book record, and `listBooks` does `getAll("books")`, so every call (each import, each search effect, each backup) deserialises every cover Blob. It is fine at a few dozen books; it grows with the library.

**Fix.** A schema version 6 migration that moves covers to a `covers` store keyed by book id, with `listBooks` returning records without them and a `getCover(id)` for cards (the object-URL hook already takes a Blob). The migration must copy and verify before deleting (the project's rule for the `folio-library` database). Tests: a migration test from a version-5 database with covers, and the existing library specs.

## 4. Search

### 4.1 The index design against the "5,000-book shelf" goal (synthetic)

**Found.** The strategy document asks for search that is "dramatically fast on a 5,000-book library". Today:

- Each book's index record stores the **full text of every page** (`pages`) as well as the inverted index (`terms`). On the three sample books the stored index is **2.0–2.3 times the text** (JSON size; the samples are 2–3 KB excerpts, so this ratio is not representative of real books; the real ratio is not measured).
- Every query calls `getAll("searchIndex")`, which deserialises **every** index, and then queries each book through the worker, which copies each index again. Synthetic cost per query (a 60-page, 18,000-word book each): about 0.3 s at 30 books, 1.0 s at 80, 3.3 s at 200, linear. In a real browser this would be several times faster, but it is still linear in the whole library's text, and 5,000 books is out of reach by design.
- The existing benchmark (`src/lib/bench.ts`) measures one book's index only, so nothing measures the path the owner's goal depends on.

**Fix (one design, in steps that each ship and are measured).**

1. **Measure first.** Extend the benchmark (or add a Playwright-driven one, since `fake-indexeddb` is not a browser) to build N synthetic books (N = 100, 1,000, 5,000; 60 pages each) and time a one-word and a two-word query and the first-result time. The owner and the next session set the budget from the baseline; a starting suggestion is a median under 150 ms at 1,000 books.
2. **Split the record.** `searchTerms` (postings only: term → pages) and `searchText` (page → text, fetched only for the hits being shown). Bump `INDEX_VERSION`; migrate in the database upgrade by splitting each record, not by re-extracting.
3. **A shelf-level map.** `shelfTerms`: term → sorted book ids, updated when a book's index becomes ready and when a book is deleted. A query tokenises, finds candidate books from `shelfTerms` (prefix handling as `candidatePages` does today), and loads postings only for those books.
4. **Stream, do not collect.** Open a cursor and process one record at a time; run the whole query inside the search worker so records do not cross to the main thread.
5. **Only then** consider an off-the-shelf engine (MiniSearch, FlexSearch). It would replace code that works, add a dependency (licence and notices work) and a persistence format to migrate; the split above is likely enough.

**Test.** The benchmark with its budget is the main test; keep the unit tests from `library-search.test.ts` (which cover which books are searched and the cap) green through every step. A migration test from a version-1 index record. A mutation on each step (for example, load text for all candidates instead of the hits) to confirm the benchmark or a test notices.

### 4.2 Indexing is on the main thread, always on, and not under the user's control (code-read)

**Found.** `indexShelfHeadless` runs while the shelf is open, one book at a time. foliate's `createDocument` needs a DOM, so EPUB parsing cannot move to a worker; pdf.js text extraction does its heavy part in its worker but post-processes on the main thread. There is no setting, no pause, and no idle scheduling beyond a one-tick yield between batches. On a phone, a first import of a hundred books could keep the page busy for a long time and warm the device; on iOS the storage it writes counts toward a quota that Safari may clear. None of this is measured.

**Fix.**

1. Settings gets "Index my books for shelf search" (on by default, since it is the headline feature) with the progress line and a "Pause" control, and a "Clear search index" next to the storage meter that already shows its size.
2. Schedule the work: take a slice per `requestIdleCallback` (or `scheduler.postTask(..., { priority: "background" })` where it exists), with a time budget per slice (about 8–12 ms), instead of one long loop per book.
3. Pause when the document is hidden (`visibilitychange`) and resume when it is visible.
4. Measure before tuning: a Playwright trace of a 100-book import with CPU throttling (`Emulation.setCPUThrottlingRate`) and the long-task count.

**Test.** Unit: the scheduler yields between slices and respects a pause. E2E: with the setting off, no book is indexed and the line says so; turning it on starts it.

## 5. Security and privacy

### 5.1 No Content-Security-Policy on the app shell (verified)

**Found.** Neither `index.html` nor `dist/index.html` has one. The privacy claim ("opening the shelf, a book or Settings contacts no other site") is enforced today only by tests and by `verify:static`; the browser itself would not stop a bug or a compromised dependency from contacting another host. Books are already protected by their own injected policy (`safe-document.ts`).

**Fix (careful; this can break the app).**

1. Add a `<meta http-equiv="Content-Security-Policy">` through the existing `inject-theme-boot` plugin in `vite.config.ts`, because the plugin already writes into `index.html`. A starting policy: `default-src 'none'; script-src 'self' 'wasm-unsafe-eval' 'sha256-<boot script hash>'; style-src 'self' 'unsafe-inline'; img-src 'self' blob: data:; font-src 'self'; media-src 'self' blob:; worker-src 'self' blob:; frame-src blob:; connect-src 'self' https://*.wikipedia.org https://*.wiktionary.org; manifest-src 'self'; base-uri 'none'; form-action 'none'`. The hash of the theme boot script is computed in the plugin at build time, so it cannot drift.
2. Know the traps: `blob:` documents inherit the creating page's policy, so the readers' iframes receive this one as well as their own (the strictest of both applies); the WebAssembly decoders need `'wasm-unsafe-eval'`; Radix and Sonner use inline styles (`'unsafe-inline'` for styles only); pdf.js, Tesseract and libarchive start workers from `blob:` or same-origin URLs.
3. A `<meta>` policy cannot be report-only, so roll it out on a branch deployed to a test Pages URL, with the console watched.

**Test.** Extend `privacy.spec.ts` so that a violation fails the run: record `securitypolicyviolation` events and console CSP errors while opening each reader type, running OCR, Define and the DjVu reader. Add a `verify:static` check that the policy exists and names no host beyond the two Wikimedia ones. Safari's handling of the `<meta>` policy in `blob:` iframes was never checked.

### 5.2 No referrer policy (code-read)

`index.html` has no referrer policy. _Define_ sends the app's origin as `Referer` (the card's text and the README should say so; the Settings notice does not). A `<meta name="referrer" content="no-referrer">` removes it. Test: extend `define.spec.ts`, which already inspects the request, to expect no `Referer` header. Effort: minutes.

### 5.3 Benchmark code ships in production; tests rely on its global (verified)

**Found.** `src/routes/__root.tsx` calls `installBench()`, so `window.__nawiriBench` and the benchmark code are in the production bundle, and every e2e spec waits for that global as its "page is ready" signal. It is harmless to users but it is test scaffolding in the product, and a readiness signal that is a benchmark is easy to break by accident.

**Fix.** Set `document.documentElement.dataset.appReady = "1"` after the first render (one line in `main.tsx` or the root effect); change the `ready` helpers in the specs to wait for it (17 spec files wait for it today, mostly through a small local helper each); load the benchmark only when the URL has `?bench` by a dynamic import. Check that the privacy and offline specs still pass.

### 5.4 The Pages workflow (verified, versions read from GitHub's release pages today)

**Found.** `.github/workflows/pages.yml` uses `actions/checkout@v4`, `actions/setup-node@v4`, `actions/upload-pages-artifact@v3` and `actions/deploy-pages@v4`. The latest releases are v7.0.1, v7.1.0, v5.0.0 and v5.0.1. Permissions (`pages: write`, `id-token: write`) are granted to the whole workflow, so the build job and pull requests carry them too. The workflow has never run (the roadmap says so). Whether the old versions still work was not tested.

**Fix.** Move the four actions to the current majors and pin each to a full commit SHA with the tag in a comment (the owner's call whether to pin); give the `build` job `contents: read` only and the `deploy` job `pages: write` and `id-token: write`; consider `cancel-in-progress: false` for the deploy (recalled from GitHub's starter workflow, not checked today). Add a Dependabot file for `github-actions`. Test: run it once with `workflow_dispatch` on the owner's repository and read the result; this cannot be done from the sandbox.

## 6. Size and weight

### 6.1 OCR cores (verified)

**Found.** The first-visit precache is 10.55 MiB, of which **7.5 MiB is the two Tesseract cores** (3.77 MiB each). `src/workers/ocr.worker.ts` names only `tesseract-core-simd-lstm.wasm.js`; the plain `tesseract-core-lstm.wasm.js` is referenced by nothing but the notices script, yet it is precached and shipped. Two consequences: 3.77 MiB is downloaded by every new visitor for no use, and a browser without WebAssembly SIMD (Safari 16.3 and earlier, from memory, not checked today) cannot run OCR at all, because there is no fallback.

**Fix (needs the owner's browser floor, see section 12).**

- If the floor is "WebAssembly SIMD everywhere" (Safari 16.4 and later, all current Chrome and Firefox): delete `public/vendor/tesseract/tesseract-core-lstm.wasm.js`, remove its entry from `scripts/make-notices.mjs`, regenerate the notices, and say in the README that OCR needs a current browser.
- If older browsers matter: detect SIMD with `WebAssembly.validate` on a small probe module, pick the core path accordingly, and keep both.
- Either way, take the cores out of the precache with a `globIgnores` entry for `**/vendor/tesseract/tesseract-core*` so only the one that is used is fetched on first OCR (the existing `/vendor/` runtime rule caches it). The cost: OCR works offline only after one online use, as DjVu does.

**Test.** `verify:static` already fails on a stray host; add a check on the precache's total size (a ceiling the owner picks). E2E: OCR a page, then go offline and OCR again. After this the first-visit download is about 3 MiB.

### 6.2 Unused UI components and dependencies (verified by script)

**Found.** Of 46 files in `src/components/ui/`, **35 are imported by nothing** (3,800 lines), and 27 packages are imported only by those files (19 `@radix-ui` packages, `cmdk`, `embla-carousel-react`, `input-otp`, `react-day-picker`, `react-hook-form`, `react-resizable-panels`, `recharts`, `vaul`). Three more dependencies are imported by nothing at all (`@hookform/resolvers`, `date-fns`, `tesseract.js-core`, whose vendored copy is what ships). They add install time, `npm audit` and update noise (24 of the 61 outdated packages in `npm outdated` are among them), and 6 of the 68 lint findings (the `react-refresh` warnings in six UI files).

**Fix.** Delete the unused components and their packages in one change, then run `tsc`, the unit tests, the build and the e2e suite; the build output should not change (they are tree-shaken today), which is itself a check (compare the precache count and size). **Keep `dropdown-menu`** if the collections alternative the owner is asked about (checkpoint 15) is built as a menu. Run `npm run notices` and read the diff. The list comes from `python3 scripts/audit/unused-ui.py` (read-only; it matches import paths, so confirm with `npm run typecheck`, the tests and a build after deleting).

### 6.3 Chunks and dynamic imports (verified in the build log)

Every build warns `INEFFECTIVE_DYNAMIC_IMPORT` for `search-index.worker.ts` (imported statically by `bench.ts` and `search-index.ts`) and for `fflate` (imported statically by `backup.ts`): the intended lazy loading does not happen, and `Some chunks are larger than 500 kB` (the entry chunk is 0.85 MiB, `es-…js` 0.41 MiB, `pdf-…js` 0.35 MiB). **Fix:** make each of those imports consistently dynamic or consistently static; split routes (`read.$id.tsx` and its readers) from the shelf with a lazy route; measure with the build's own chunk table and a Lighthouse-style first-load number on a throttled profile. Effort M, and not urgent while the precache is the cost that matters (6.1).

### 6.4 The browser test suite (measured)

The full run is 6.8 to 7.3 minutes on one worker on a two-core machine (6.8 in checkpoint 19, 7.1 and 7.3 in checkpoint 20); the slowest spec files are `safe-reading` (72 s), `a11y` (69 s), `djvu` (45 s). There are 14 `waitForTimeout` calls in six files, which are timing bets. **Fix:** try `workers: 2` (each test uses its own context, so isolation should hold; not tried), replace each `waitForTimeout` with a condition, and watch for flakiness over ten runs before trusting it.

**A spec that failed once (verified that it happened; cause not established).** In the first clean-extract run of checkpoint 20, `tests/e2e/reader-pages.spec.ts` › "Alt + arrow reorders a page and announces the move" failed: the polite announcement span stayed empty for the whole 30 seconds. The same spec passed in the working-tree run, in the next full run of the same extract, in 15 isolated repeats and in 6 repeats of its whole file: 1 failure in 24 attempts. The failure's trace was overwritten by the isolated repeats (the `test-results/` folder is cleared by each run), so the cause was not read from it. What the code allows, as hypotheses: the test focuses the "Go to page 1" button and presses the key at once, and `onGridKeyDown` in `src/components/reader/drawer/pages-tab.tsx` returns **without a word** when `pageOps` is busy, so a key pressed during an operation, or with focus not yet on the button, produces no announcement. **Next step if it recurs:** copy `test-results/` before running anything else and read the trace. **Likely fixes, once the cause is known:** have the test wait for the page-1 thumbnail (as its neighbours do) and for focus (`toBeFocused`) before pressing the key; and have the handler announce "Busy, try again" instead of ignoring the key (a screen-reader user gets no feedback today; this part is a reasoned gap, not a measured one).

## 7. Accessibility

### 7.1 Reduced motion (verified: zero references in `src/` and `index.html`)

**Found.** Nothing reads `prefers-reduced-motion`. The HTML reader sets `scroll-behavior: smooth` and calls `scrollIntoView`/`scrollBy` with `behavior: "smooth"` in six places; the interface uses Radix `animate-in`/`animate-out` (37 uses) and about 110 `transition-*` classes; whether foliate animates page turns by default was not checked.

1. `src/styles.css`: a global `@media (prefers-reduced-motion: reduce)` block that sets `animation-duration`, `animation-iteration-count` and `transition-duration` to near zero and `scroll-behavior: auto`.
2. `html-reader.tsx`: one helper, `const smooth = () => matchMedia("(prefers-reduced-motion: reduce)").matches ? "auto" : "smooth"`, used in the six places, and the injected style in the iframe gets the same media query.
3. foliate: check the paginator's animation attribute and switch it off under the same query; the comic reader's guided-view transitions the same way.
4. Auto-scroll (a moving page the reader did not ask to move each time) already has its own switch; confirm it starts off.

**Test.** Playwright with `page.emulateMedia({ reducedMotion: "reduce" })`: a computed `transition-duration` of 0 on a button, and a jump to a contents entry in an HTML book that lands with no smooth scroll (compare `scrollY` immediately after the click). Mutation: remove the media block and watch it fail.

## 8. Product

### 8.1 Importing by dropping files or folders (verified: no drop handler on the shelf)

Only a book-to-collection drag exists (`collections-sidebar.tsx`). To add books a person must use the file dialog. **Fix:** a drop target on the shelf (`onDragOver`/`onDrop`) that takes `event.dataTransfer.files` into `importFiles`; for folders, read `DataTransferItem.webkitGetAsEntry()` recursively, and add a "Choose a folder" button with `<input webkitdirectory>`. Show the drop target to keyboard users as the existing button (the button remains the accessible path). **Test:** Playwright `dispatchEvent("drop", { dataTransfer })` with a DataTransfer built in the page; and a folder case through the input with `setInputFiles` on a directory.

### 8.2 Import messages (code-read)

"N already on your shelf" does not say which, and "Couldn't read: … (is empty)" is English only. **Fix:** list the first names and link to the existing book's card ("`x.epub` is already on your shelf as _Walden_"); keep the strings in one place so a later language pack (a roadmap item) can replace them.

### 8.3 One search over titles, notes, highlights, tags and text (reasoned)

The strategy's headline P0 is "title, author, note, highlight, tag, and annotation". Titles, authors and tags are searched; the per-book index has a `notes` field (`indexAnnotationText`) that is filled only from the reader (`reader-shell.tsx`), so a book that is not open has no note text in its index; the shelf's "In your books" section lists text hits only. **Fix:** feed annotation text into the book's index record whenever an annotation changes (not only when its reader is open), and show one ranked list with a label per hit type (title, note, highlight, text) and the same jump. Depends on 4.1 (do not build it on the current record layout). **Test:** create a highlight with a note in a book that is then closed, search the note's words from the shelf, and land on it.

### 8.4 Diagnostics without telemetry (reasoned)

With no analytics by design, a problem on the owner's iPhone reaches the developer as a screenshot. **Fix:** Settings → Privacy gets "Copy diagnostics": app version, browser string, counts (books, indexes, failures), the storage estimate, which features the browser lacks (`WebAssembly SIMD`, `showSaveFilePicker`, `CompressionStream`), and the last few caught errors, with no titles, file names or text. Shown in a dialog before copying, so it is not a hidden channel. Test: a unit test that the output holds none of a seeded book's title.

### 8.5 Open files from the operating system (reasoned)

A `file_handlers` entry in `public/manifest.webmanifest` and a `window.launchQueue.setConsumer` that passes the handles to `importFiles` lets an installed Chromium app take "Open with Nawiri". Not available on iOS or Firefox. Effort M, with the file-handle permission flow the main risk. **Test:** the consumer as a unit test with fake handles; the OS integration is manual.
